# 中文写作规范

本文是对个人中文写作经验的整理，涵盖软著、专利、论文、博客、实验记录等场景，按需取用。本仓库的软著写作以`guidelines/`各阶段指南为准，本文只作可选的风格参考。

判断标准只有一条：**把这个词删掉，这句话损失信息吗？没损失，它就是填充物。** 有损失，就留着。自己改稿的土办法是：搜出一个词，盯着它问三秒——你在干嘛？答不上来，删；答得上来，留。不光盯着示例词，要通读全文，删掉一切没信息的内容。

## 一、去AI味

- 像真人写，不要AI化、不要废话；解释性的话简洁地放在外面。
- 清理固化句式：不要反复套用同一种升华表达，换地道的句式，用同义词替换。
- 删具体AI词：把“明显”“口径”“权重口径”改成具体说法（如“加权方式”），不要用“口径”这类AI味表达。
- 去掉辩解、防御语气：不必用辩解语气，直接陈述数据来源。
- 别复述没看数据的话：批判性看待AI的回复，因为它不一定看过数据。
- 删AI式补充说明、免责脚注：这类明显的AI补充说明全文都要清掉。方法部分清AI句式、不升华；讨论部分可以升华，但句式要换、不能模板复用。

## 二、少否定 / 不防御性 / 直击重点

- 太多“不是”“口径”这类词时，要替换说法。
- **“不是…而是…”句式全文清零**：包括“并不是…而是”“不再只是…而是”“X，而非Y”“不能只A，要B”“也不限于A，还包括B”。改法：对比信息的前半句通常已隐含后半，直接写正面陈述。纯对比可留“区别于X”。写完用正则扫 `不是.{0,12}而是|而不是|而非|不再|并不能只`，应为0。
- 都要用中文标点，并且直击重点、不绕弯子、不防御性。
- 别用引号把普通词框成“术语感”。
- 对外文档不暴露内部痕迹：读者只需要结果与必要方法，内部校对、预计算过程不写，不要露出“假装跑过”的痕迹。
- 别给读者讲正文没讲的事：说明越多越怪，弱化或删掉正文没有交代的背景。

## 三、长段落拆分 + 短段落/短列表合并（两端都要）

- 拆长段：扫描所有超长段落，适当拆分子列表，去重复、废话、AI味；每一段只讲一个要点、一个key point，像论文一样条理清晰；每段都有中心句、重点突出。
- 合并过短的：每一行/每一条至少20字，短段落适当合并，每条不超过200字，长的用嵌套子列表；不是所有段落都要合并，但不该只有个位数长度。
- 不要中途断行：一句话没写完就换行、频繁换行都要避免，太短的都弄连贯点。

## 四、中文标点 + 数字/英文与中文间无空格

- 用中文标点，尤其是引号；除非是英文回复。
- **数字/英文和中文之间不要空格**：写“口试B”“书页63/70”“2010版”“表6”“图4”“120个motif”“MD模拟”“AI制药”，不要写“表 6”“图 4”“MD 模拟”这类。
- 图/表编号格式：写“图10.”而不是“图10”；markdown里 `## 3.1` 这种heading后面还是要空格。
- **斜杠用英文半角 `/`**：并列、比值、对照一律写半角 `/`（train/test、80%/10%/10%、分子对接/MD），不写全角 `／`。写完可用 `s.count('／')` 扫一遍，应为0。

## 五、加粗 + 引用块（punchline）

- 关键点适当加粗；完全不加粗也要补。
- 列表不要只在最开头加粗；没必要的加粗可以去掉。
- 引用块是punchline而非复述：要比加粗更突出的内容才用引用块，得是take home message，不是前面内容的概括重复；背景、结果处适当补引用块。
- 负号不要放进加粗里。

## 六、精简 / 去重复废话 / 表格与正文分工

- 精简描述，别废话，去掉重复和没用的话。
- 表格与正文分工：括号解释别写进表格，写进段落；有表格时正文不大量重复数据，只写关键结论；列数太多的精简列数，转成表外文字。
- 图注（caption）长度：太长的拆成列表或段落；如果正文内容已经体现，可以干脆取消图注。
- 图注不写正文结论：caption只说明图表本身，结论进正文。
- 图表编号与引用顺序：图表按正文引用顺序编号；附录图也必须在正文相应位置提到，不能完全不引用；引用顺序乱了优先调图而不是调文字。
- punchline位置：在引言最后一段、结果相关部分、讨论第一段分别体现。

## 七、专业名词规范

- 不常见的专业名词首次出现写全称，后续可只用简称。
- 不要截断专业名词（如“Pearson correlation”应为“Pearson correlation coefficient”）。
- 统一 + 准确：同一个词尽量统一；统一美式拼写（maximise→maximize）；校准专业名词的译法。
- 陌生概念要解释：多解释读者可能不熟悉的名词和统计量，说人话，不要太晦涩。

## 八、英文写作句法（头重脚轻）

- 避免过长主语+过短宾语，谓语拖太久才出现会让读者难受；读者在主语后立刻想看到谓语动词，主语与动词隔太远会打断阅读，把定语、修饰语尽量后置（与中文习惯相反）。

## 格式一致性 / 前后逻辑 / 可读性

- 检查逻辑是否矛盾、前后是否对应得上、读者是否读得通。
- 公式/下标：公式和 `$$` 两边要换行；该下标的都要真的下标；等号两边要空格；简单分数不进公式。
- 单位与符号全文统一：同类量全文用一种单位写法，避免每个表头都写单位导致表头太长，可在开头全局说明一次。
- 有效数字精简：`R^2 = 0.828345` 这类不用写这么多位；`188s≈3.1min` 这类只留min。
- heading层级：太多同级标题要适当归类；相邻层级之间不要空着，要有总览或内容。

## 九、推文/科普文体

- 开头先抓人：开头只简单提一个观点不够，一开头就扔出重磅想法，再用论文或博客佐证。
- 稍微有点故事感，更能吸引读者、更engaging，但不要违反平台相关规定。
- 忌理论堆砌：过多理论堆砌让人难以代入，要加点具体情境。

## 十、软著专属

### 文档体系与定位

- 软著分两种文档：**用户手册**（描述用户怎么点、截图即可，写简单）和**源程序文档**（贴代码）。两者字体要一致。
- 用LaTeX编写，走softcopy-toolkit工具链。
- 体量原则：交存一般取前后各连续30页；总量不足60页全部提交。源程序没有“3000行上限”这类硬规定，不要为凑行数虚构代码。

### 代码副本与排版（工程规范）

- 以`src`为主：软著代码用`src_prod`（由`init_code_copy.py`生成、必须去掉空行）；本仓库为示例已提交一份`src_prod`，自己的项目可按需决定是否纳入版本管理。
- 用 `--remove-empty` 就地改写软著包内副本，但不能改写最初源。
- 代码块用lstlisting：用户手册可带边框底色，源程序文档用纯白底无框；里面不要反斜杠转义。
- 保持彩色高亮；不超宽、不要内部换行导致不美观；列表（有序/无序）必须缩进，不能顶格。正文段落按模板约定顶格不缩进。
- 图表尽量钉在当前位置；删冗余单个标题；代码不必要换行收一收以减页数。
- 最终PDF要查编译log、查“刚好多一点点导致换行”的，缩一缩省行；表格跨页大片空白要修，不能只调小字体。

### 文字与表达规范

- 去AI味：删套话、升华句式、防御性表述；删“没啥意义很快换行”的。
- 术语一致且正确：校对专业名词，避免错误说法；同类概念统一用词。
- 中文标点：数字/英文和中文之间不要空格；标题不要奇怪反斜杠；公式用行间公式。
- 正文段落顶格不缩进（与模板easybook排版一致）；长段落适当拆分；item超长也可拆子列表。
- 不要写“具体版本以封存环境为准”“两项任务合计约N分钟”这类不该给专家看的话；删无关废话。
- 第一章不要堆太多技术细节/代码，适度合并到后面的章节；全文重复表述去重。

### 图文与图表

- 图文融合：图放合适位置、和内容匹配，不要图文分离；图注倾向简洁。
- 架构图要求：框内字太多/太丑/空白多就拆分框、长宽均衡、每框字少；分辨率达标；太大就缩小，考虑横版。
- 截图：用户手册描述操作+截图即可，最终不用放太多图，意思到位就行。
- 必须有个images目录。

### 与代码/项目口径对齐

- 软著必须与代码一致：函数名、参数、支持的选项等逐项核对。
- 功能口径：用户可调的参数要在文档说明代码是否支持；说明提供的各种入口。

### 提交与归档

- 通常不追踪生成的PDF；本仓库的`document.pdf`与`source-code.pdf`是完整示例成品，作为例外已提交。
- 申请表用application.md，据其修改文档。
- 新建软著：复制一份已有文件夹再改；按softcopy-toolkit/init_code_copy.py --force重建代码副本。
